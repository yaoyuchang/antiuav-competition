# 泛化性测试用例

5 组独立、完整的 4 文件 CSV 配置包（每组都含 obstacles.csv / start_points.csv /
goal_points_initial.csv / goal_points_changed.csv，可直接用
`--config-dir ../config_tests/<组名>` 跑，不会有任何字段静默回退到硬编码默认值）。
基线是 `code/config/` 下的官方数据；这里每组只改变一个维度。

跑法：
```bash
cd code/run_example
python run_with_config.py --config-dir ../config_tests/01_goal_order_shuffled \
  --mode competition --cycles 2000 --output /tmp/x.json --seed 0
python evaluate_metrics.py --input /tmp/x.json
```

## 结果一览（competition 模式，种子 0）

| 组 | 改动 | 结果 | 失败层级 |
|---|---|---|---|
| 01_goal_order_shuffled | 24个初始终点z值顺序反转（值不变，分配变了） | ❌ 第382周期失败，76.4s | 单机自身无解 |
| 02_starts_compressed | 起点z范围 ±40→±20（压缩一半） | ❌ 第0周期失败，0s | 起飞瞬间即违规 |
| 03_mirrored | 起点/终点/障碍物z坐标全部取负 | ❌ 第519周期失败，103.8s | 单机自身无解 |
| 04_extra_obstacles | 新增2个静态障碍物（编号20/21） | ❌ 第385周期失败，77.0s | 多机协调无解 |
| 05_goals_expanded | 初始终点横向散布扩大一倍 | ✅ 583周期成功 24/24，116.60s | — |

## 每组细节

### 01_goal_order_shuffled
`goal_points_initial.csv` 的 z 值顺序整体反转（原第1行的值现在给第24行，以此类推）。
起点顺序不变。

**暴露的问题**：高度分层按 `机号 % 3` 分组，机号和起点z是绑定单调的；横向走廊
的等比缩放假设终点z顺序和机号顺序一致。这里只打乱了终点分配、起点不变，导致
原本该去左边终点的机现在要飞到最右边——终端区变成大规模交叉穿越而不是错落
汇聚。**当前方案隐含假设"起点排列顺序和终点排列顺序对应"，题面数据里这个假设
成立（两张表都按机号单调排列），但不保证评委给的数据也这样。**

### 02_starts_compressed
`start_points.csv` 的 z 坐标整体乘 0.5。

**这组测试设计本身有问题，不是代码 bug**：题面给定的起点间距是 3.478 米，已经
只有 3 米安全线的 116% 余量，压缩一半后间距变成 1.74 米，飞机还没起飞就已经
违规（`swarm_coordinator.py:88-90` 的起飞前置校验直接拦下）。**说明起点密度
没有再压缩的空间了，题面给的起点排列已经是极限，这个维度上"更密"不是一个能
测的方向，除非重新设计起飞队形（比如起飞时也分层，不只是一条直线）。**

### 03_mirrored
起点、两张终点表、障碍物表的 z 坐标全部取负（真正的整体镜像，不是只镜像无人机）。

**结果需要打折扣看待**：10/11/12 号障碍物（运动的旋转长方体）的旋转角度和
运动方向在代码里是硬编码的（`math.radians(30.0)`，固定的运动方向向量），
不是从 CSV 读出来的，镜像 z 坐标并不会让这几个动态障碍的运动方向跟着镜像。
**这不是一次干净的对称性检验**——失败很可能是这个不对称的动态障碍造成的新
遭遇，不能就此断言代码存在方向性偏见 bug。如果要做干净的镜像测试，需要额外
让运动方向配置也能镜像。

### 04_extra_obstacles
在官方19个障碍物基础上加了2个静态障碍物：
- 20号：圆柱，x=800, z=50，半径40，高45（早段巡航区）
- 21号：立方体，x=4200, z=250，100×60，高60（切换区/下降归位区附近）

**首次诊断有误，已用更精确的失败诊断（`blocker_contribution_counts`而不是
`blocking_uav_ids`——后者只是"这一轮已预约的全部机"，不是真正造成冲突的机）
重新定位，结论是完全不同的机制**：真正卡住的不是4200米那个障碍物，而是
**3500米切换点附近，两架已经切换、处于同一高度层的机各自独立算出的新航路
横向重叠**（第385周期，UAV19与UAV10同在60米层，横向只差约2米，UAV10单独
就排除了UAV19全部34条候选）。根因是L1对"同层还有别的机"完全无感知——切换后
每架机独立规划直奔各自新终点，如果两架恰好当前位置相近、新终点也相近，算出的
新航路就可能撞在一起。

已经给切换后的重规划加了"高度维持"（详见 `mamp/planners/route_shaping.py` 的
`shaped_switch_route`）：切换瞬间不立即拉平到统一高度，而是保持切换前的高度层
飞完本段一半再降到新终点高度。**两个官方门槛场景（硬编码基准、CSV场景）都验证
仍是583周期成功24/24，没有退步**；但这次失败发生在同层内部，高度维持这个手段
覆盖不到，所以测试4依然在第385周期失败（数字和之前一致，没有变差）。如果要修
这个具体案例，需要给切换段重新加回横向走廊——但走廊偏移量不能直接照搬首段公式
（首段终点z最大±130米，切换后终点z最大到±575米，同样的倍数会把偏移推到网格
边界±680米外，第一次尝试就是这样炸的），需要限幅后再测。

### 05_goals_expanded
`goal_points_initial.csv` 的 z 值以均值为中心整体拉伸2倍（散布从130米扩到460米）。

**验证了预期方向**：终端区更分散确实更容易——机间裕度 3.028m（比基准 3.010m
还宽）、能耗 619.4（比基准 625.9 低）、平滑性 0.985（比基准 1.104 好）。
说明往"更宽松"方向泛化没有问题，当前方案的脆弱点集中在"更密集 / 顺序不对应 /
障碍物数量变化"这几个方向，不是泛化性整体存在问题。
